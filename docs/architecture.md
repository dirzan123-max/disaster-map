# 設計メモ

作るときに迷った点と、なぜその形にしたかを残しておく。

---

## 出発点

もとは職場で「災害の発生を捉えて、地図で示したい」という話があり、
Power BI + PowerShell で作ったものが `re/`（jma-alert-map）にある。
あれは Windows と Power BI Desktop が前提で、担当者が席にいないと見られない。

BCP の用途では **持ち歩けること**と**自動で気づけること**が要るので、
アプリ／Web として作り直したのがこのリポジトリになる。

---

## 1. 全ソースを1つのモデルへ正規化する

`DisasterEvent`（`lib/domain/disaster_event.dart`）に寄せている。
地図・一覧・通知・Webhook は、元の API の形を一切知らない。

これで新しい取得先を足すときの作業が「Source クラスを1つ書く」だけになる。
逆に、正規化しきれない情報（気象庁の細分区域ごとの詳細など）は
`details` という文字列リストに逃がし、モデルを肥大させないようにした。

### 深刻度は 0〜4 の共通スケールに写像する

震度・マグニチュード・警報の種類・噴火警戒レベルは、そのままでは比較できない。
`Severity`（`lib/domain/severity.dart`）で 5 段階に揃えている。

| | 日本 | 世界 |
|---|---|---|
| 4 重大 | 特別警報 / 震度6弱以上 / 大津波警報 / 居住地域に及ぶ噴火警報 | M7.0以上 |
| 3 警戒 | 警報 / 震度5弱・5強 / 津波警報 / 入山危険 | M6.0以上 / 火山・洪水 |
| 2 注意 | 注意報 / 震度3・4 / 津波注意報 / 火口周辺警報 | M4.5以上 / 暴風・山火事 |
| 1 軽微 | 震度1・2 | M4.5未満 |
| 0 情報 | 解除など | — |

**この表がアプリ内の唯一の基準**で、地図の色・凡例・通知しきい値がすべてこれを見る。
利用者が「赤は何を意味するか」を一度覚えれば済むようにするため。

絞り込みで選べる下限は「軽微・注意・警戒・重大」の4つにしてある。
「情報以上」は全件表示と同じで、選択肢として働かないため外した。
代わりに、震度もマグニチュードも分からず `info` になった情報を
切り捨てないよう、絞り込みの判定では `info` を `minor` と同じに扱う
（`Severity.forFilter`）。

## 2. 座標を持たない情報をどう扱うか

気象庁の警報は「区域」、噴火警報は「火山」、津波予報は「予報区」で発表され、
**応答に座標が入っていない**。地図に出すには座標が要る。

| 情報 | やったこと |
|---|---|
| 気象警報 | 気象庁が公開している一次細分区域のポリゴン（`geojson/class10s.json`）から代表点を計算し、143件をアプリに同梱 |
| 噴火警報 | 気象庁の火山一覧（`volcano_list.json`）に座標があるので、117件をそのまま同梱 |
| 津波予報 | 予報区の代表点が手に入らないため、**地図には出さず一覧にだけ出す** |

代表点は「最大面積のポリゴンの重心」にしている。単純な平均だと、
離島を多く持つ区域でピンが海上に落ちるため（`tool/build_assets.py`）。

`DisasterEvent.latitude` を nullable にして、`hasLocation` が false のものは
一覧に「地図なし」と添えて必ず現れるようにした。**地図に出せないことを、
情報を捨てる理由にしない**というのがここでの方針。

## 3. サーバーを持たない

中継サーバーを立てれば、CORS も認証もレート制限も自由に扱える。
が、個人で続けるには運用費と手間が重い。

そこで **CORS が許可されている取得先だけを選んだ**。
実際に `Access-Control-Allow-Origin` を確認してからソースを決めている。

| 検討したが採らなかったもの | 理由 |
|---|---|
| ReliefWeb API | appname の事前申請が必要 |
| GDACS | エンドポイントによって CORS の扱いが不安定 |
| CARTO のベースマップ | API キーが必要になり、地図に透かしが入る |
| FCM によるプッシュ通知 | 送信側にサーバーが要る |

通知は「端末が15分ごとに自分で取りに行き、条件に合えば自分で鳴らす」方式にした。
これならサーバーが要らない。代わりに**即時性は15分刻みが上限**になる
（Android WorkManager の最短間隔）。速さが要る用途は GitHub Actions 側の
定期監視（`tool/watch.py`）で補う、という役割分担にしている。

## 4. 失敗したときに何を見せるか

災害情報は「取れなかった」ことが分からないのが一番まずい。

- 1つのソースが落ちても、他のソースの結果は表示する
- ただし**どのソースが落ちたかを画面に出す**（`DisasterSnapshot.failures`）
- 全部落ちたらキャッシュを出し、**「保存済みの情報です」と明示**する
- 日本の地震だけは、P2P地震情報が落ちたときに気象庁の一覧へ切り替える
  （一次情報源だが 600KB あるので、平常時は叩かない）

## 5. 検証を外部 API に依存させない

各 API の実際の応答を `test/fixtures/` に保存し、パーサはそれに対してテストする。
ネットワークが要らないので CI で安定して回り、
`tool/refresh_fixtures.sh` で取り直したときに**仕様変更があればテストが落ちる**。

特に落としたくない間違いを名指しでテストしている。

- GeoJSON の `[経度, 緯度]` を取り違えていないか
- 日本時間を UTC に直しているか（9時間ずれ）
- 気象庁の続報が並んでいるとき、同じ地震を重複させていないか
- 区域コードから座標を引けているか（引けないと地図から消える）

## 6. Web で踏んだこと

- **日本語フォントを同梱していないと、初回表示が豆腐（□）になる。**
  さらに悪いことに、文字幅の計算が実際の描画とずれるため、
  チップやボタンのラベルが途中で欠ける（英語ラベルでは起きない）。
  4.5MB 増えるが Noto Sans JP を同梱して解決した。
- **Slack などの Incoming Webhook はブラウザから直接叩けない**（CORS 非対応）。
  Web版では送信内容を提示するにとどめ、実送信はアプリ版か GitHub Actions に任せている。

## 6.5 地図は1つにする

もとは「日本版／世界版」を切り替える形にしていた。しかしこれは
**情報源の都合であって、利用者の関心ではない**。切り替えを残した結果、
「世界版に日本の地震は出るのか出ないのか」が種別によって変わり、
説明できない状態になった。

そこで地図を1つにして、情報源はアプリが自動で使い分けることにした。

- 日本国内の地震・津波・気象警報・噴火警報は気象庁（震度・警戒レベルつき）
- それ以外は USGS と NASA
- 同じ出来事が両方から来たら、**気象庁が扱う種別に限って**世界の配信元のぶんを落とす
  （`_withoutJapanDuplicates`。気象庁が扱っていない台風・山火事は国内でも残す）

**「日本にしかアイコンが立たない」誤解はグレー表示で防ぐ。**
種別は単一選択なので、選んだ種別の情報源が無い範囲は必ず塗れる。
気象警報を選べば日本以外が全部グレーになり、
「日本でしか起きていない」ではなく「日本しか見ていない」ことが分かる。

地図タイルは OpenStreetMap 1種類にした。地理院タイルは国内だけ美しいが
国外が真っ白になるため、1枚で世界まで見せるこの構成では使えない。

## 7. どこまで取れているか

配信元を実際に叩いて数えた（2026-08）。

| 種別 | 取得範囲 | 実測 |
|---|---|---|
| 地震 | 全世界・30日（M4.5 未満は直近24時間だけ） | USGS 直近24時間 283件のうち約250件が米国内。過去30日の M4.5 以上は 665件 |
| 火山 | 全世界 | 噴火中として登録された14件（チリ・ロシア・PNG・日本など） |
| 暴風・熱帯低気圧 | 全世界 | JTWC などの現況 6件 |
| 山火事 | **米国のみ** | 情報源が IRWIN（米国の消防データ）で、国外の火災は入らない |
| 洪水・地すべり | 全世界だが登録が非常に少ない | 開いている事象が 0 件のことが多い |
| 気象警報・津波 | **日本のみ** | 気象庁だけを使っているため |

取れない範囲を白いままにすると「そこでは何も起きていない」と読めてしまう。
そこで **表示中の種別の情報源が無い範囲を地図上でグレーに塗る**
（`lib/data/coverage.dart`、`DataCoverage`）。山火事なら米国以外がグレーになる。
範囲内でも完全ではない点（M4 未満の取りこぼしなど）は、
地図の左上に但し書きとして出す。

### 地震は「直近は細かく、過去は大きいものだけ」

USGS のまとめフィード（`summary/all_day.geojson`）は直近24時間しか無い。
過去に遡るには同じ USGS の検索API（FDSN `fdsnws/event/1/query`）を使う。
提供元が同じでキーも要らず、CORS も許可されているので乗り換えの影響は小さい。

ただし全マグニチュードで30日遡ると数万件になり、地図が持たない。
そこで **直近24時間はまとめフィード（小さい地震も含む）、
それ以前は検索APIで M4.5 以上**という二段構えにした（実測 665件）。
ID の体系が同じなので、重なった分は素直にまとめられる。
検索APIが落ちても直近24時間の表示は止めない。

気象庁側の P2P地震情報は `limit` を 50 から 100（API の上限、おおよそ1週間分）に上げた。

### EONET はカテゴリごとに分けて取る

当初は全カテゴリを1回のリクエストで取っていたが、
`days=120&limit=300` にすると **300件中293件が山火事**になり、
噴火中の火山が1件も入らなくなった。EONET の日付は「最後に観測された日」で、
現象ごとに続く長さが違うためで、カテゴリごとに遡り日数と件数を変えて
並列に取る形にした（`EonetSource.defaultCategories`）。
一部のカテゴリが落ちても、取れた分は表示する。

## 8. 絞り込みを画面と通知で共有する

| 絞り込み | 効く範囲 | 置き場所 |
|---|---|---|
| 災害種別（単一選択・必ず1つ） | 画面のみ | 地図の上 |
| 深刻度の下限 | 画面のみ | 地図の上 |
| さかのぼる期間 | 画面と通知 | 地図の上 |
| 国・地域 | 画面と通知 | 設定画面 |

いずれも選んだ内容は端末に残る（`NotificationSettings`）。
国だけ設定画面に置いているのは、しょっちゅう変えるものではないため。
そのぶん「今は絞り込まれている」ことが見えなくなるので、地図の下の帯に
「国: 2か国に限定中」と出す。

種別を複数選択から**単一選択**に変えたのは、今どの情報を見ているのかが
分かりにくかったのと、グレー表示が種別ごとに決まるため。
「すべて」は置かず、取得できた種別の先頭を既定にしている。

国の絞り込みは、情報源が全世界を対象にしている種別にだけ効く。

さかのぼれる長さは種別ごとに違う（`DataCoverage.historyOf`。
地震30日・火山1年・台風14日・山火事10日・洪水60日）。
配信されていない長さを選択肢に出すと、「30日で見ているのに何も無い」のが
絞り込みのせいなのか情報が無いせいなのか分からなくなるため、
**選択肢そのものを取れる範囲までに制限**している。

- 選べるのは上限までのプリセットだけ（山火事なら 10日 まで）
- 「制限なし」は「すべて（最大10日）」と、実際の長さを添えて出す
- 種別を変えて上限を超えたら、その場で上限まで縮める
- 気象警報のように「今出ているものだけ」が配信される種別は、
  期間ボタン自体を押せなくして「今出ているぶん」と表示する

細かい注記を並べるより、選ぶ場所で上限が見えるほうが伝わる。

期間（`TimeWindow`）の選択肢は「直近30分」から「直近30日」までの上限だけを並べ、
「1時間前から2時間前まで」のような範囲は「範囲を指定…」から都度決める。
欲しい区切りが用途によって違うため、固定の選択肢にはしていない。

既定は直近24時間で、**選んだ期間はそのまま端末に残る**。
「常に直近24時間だけ見たい」「30日をまとめて見たい」は人によって分かれるため、
アプリ側で毎回決め直さず、前回の選択を使う。

### 「継続中」でも、起きた時刻は取れる

EONET は継続中の事象（`status=open`）だけを配信するが、
`geometry` は時系列の配列で、**最初の1点が起きた（探知された）時刻**になっている。
台風なら経路の起点、山火事なら探知日時。
当初は「継続中だから期間で絞れない」として全部を絞り込みの対象外にしていたが、
これは誤りで、期間を変えても件数が変わらない状態になっていた。

位置は最新の1点、時刻は最初の1点を使う。最新の観測時刻を採ると、
続いている限り常に「今」になってしまい、期間の絞り込みが効かなくなる。
最終観測の時刻は詳細に添える。

### 継続中でも、期間の絞り込みからは外さない

気象庁の警報（`warning/map.json`）は**今発表中のものだけ**を配信していて、
`reportDatetime` は「その府県予報区で最後に発表・更新された時刻」でしかない。
実際、注意報が継続中なのに `reportDatetime` が3か月前のまま、ということが起きる。

一度は「継続中のものは期間の絞り込みから外す」形にしたが、これは失敗だった。
**期間を変えても件数が1件も変わらず、絞り込みが壊れているように見える。**
（噴火警戒レベルは何年も前の発表のまま続くため、直近30分にしても
2025年の情報が残っていた。）

いまは `DisasterEvent.isOngoing` を**表示の書き分けだけ**に使い、
絞り込みはすべてのイベントに同じように効かせている。
一覧では「継続中」と表示し、時刻には「更新」を添えて、
それが発生時刻ではなく最終更新であることが分かるようにしている。

気象警報を「直近24時間」で見ると、24時間以内に更新された警報だけになる。
絞り込みで消えているのか、そもそも無いのかが分からないと壊れて見えるので、
0件のときは「◯◯で絞り込んでいます」と現在の条件を出し、
「期間の絞り込みを外す」ボタンを置いている。

### 取得できているのに中身が古い、を検知する

実際に、気象庁の警報 API（`bosai/warning/data/warning/map.json`）が
**3か月更新されていない**ことがあった（`Last-Modified` が5月28日のまま）。
地震のほうは同じ日の新しいデータが来ていたので、警報だけが止まっていた。

取得は成功しているので `failures` には出ず、期間で絞ると黙って0件になる。
これでは絞り込みのせいだと誤解される。
そこで「毎日のように更新されるはずの種別」（今は気象警報）について、
最新の時刻が3日以上前なら `DisasterSnapshot.staleKinds` に記録し、
帯に「気象警報の配信が止まっています（最新 5/28 11:32）」と出す。

### 気象警報は防災情報XMLから取る

そこで気象警報は **防災情報XML**（`developer/xml/feed/extra.xml`）に切り替えた。
こちらは生きていて、発表の数分後にはフィードに並ぶ。

- フィードに発表の一覧（約400件、うち気象警報が120件ほど）
- 各エントリの XML に `ReportDateTime`（**発表時刻**）・警報コード・
  一次細分区域コードが入っている
- 区域コードは bosai と同じなので、**同梱の代表点表と警報コード表がそのまま使える**

bosai の JSON に無かった「いつ発表されたか」が入るので、期間で絞り込める。

制約は1つ。フィードだけでは中身が分からず、府県ごとの個別XMLを開く必要がある。
全国だと最大58本になるので、**新しい順に20件**へ絞り、
取りこぼした府県は次の更新で拾う（`JmaWarningXmlSource.limit`）。

CORS は許可されている（`Access-Control-Allow-Origin: *`）ので Web 版でも使える。
一度「CORS 非対応だから Web は bosai のまま」と判断したが、これは誤りだった。
`Origin` ヘッダを付けずに応答ヘッダを見ていたため、
CORS のヘッダが返ってこなかっただけ。**確認するときは `Origin` を付ける。**

なお、**過去に出ていた警報を遡って見ることはできない**。
気象庁の無償APIは現在発表中のものしか持たず、防災情報XMLの長期フィード
（直近1週間）は CORS 非対応でブラウザから叩けないうえ、
1週間で1万件近いエントリを個別に取りに行く必要がある。
ただし**通知では下限を無視する**。「1〜2時間前だけ通知」は、
起きた直後の情報を取り逃がすことになるため
（`TimeWindow.containsForNotification`）。

国は Natural Earth の国境（239件）を同梱し、座標から判定している
（`tool/build_countries.py` → `assets/countries.json`、`CountryIndex`）。
まとめて指定するか、種別ごとに変えるかを選べる（`CountryFilter`）。
**切り替えても、もう一方で指定した内容は消さずに持ち続ける。**
誤って触ったときに設定をやり直す羽目になるのを避けるため。
消えないことが分からないと切り替えるのが怖いので、
切り替えの真下に「◯件は消えていません。戻せばそのまま使えます」と出す。
**情報源が最初から一国に限られている種別（山火事＝米国の消防データ）は、
国で絞らずに素通しする。** 絞っても「その国か、全部消えるか」にしかならず、
利用者からは壊れているように見えるため。

- 判定は取得直後に一度だけ行い、`DisasterEvent.countryCode` に持たせる。
  絞り込みのたびに国境を調べ直すと、件数×239か国の計算が毎回走る
- 陸上は交差数判定、海上は 300km 以内で最も近い国に寄せる
  （「日本の東方沖」を日本の絞り込みで拾うため）
- どの国にも寄せられない外洋のイベントは、既定では**表示する**側に倒す
- ISO_A2 が `"CN-TW"`（台湾）のような値で入っている行があり、
  先頭2文字で切ると中国と衝突する。2文字の英字のときだけ採用している
- 同じ国コードの地物が複数ある（オーストラリアとアシュモア・カルティエ諸島など）。
  領域は足し合わせ、名前は面積が最大の地物のものを採る

検索は「にほん」「アメリカ」でも当たるよう、ひらがなを片仮名に寄せたうえで
別名表（`ALIASES`）も引く。正式名称が「アメリカ合衆国」「大韓民国」のため、
そのままでは日常の呼び名で引けない。

## 9. 通知は種別ごとに強さを決める

深刻度は**種別ごとに**決める（`NotificationRules.severityByKind`）。地震は警戒以上でよくても
津波は注意報から知りたい、というように種別で重さが違うため。
「通知しない」も同じ並びから選べるようにして、
「種別の選択」と「深刻度の設定」を1つの操作にまとめている。

選べるのは「注意以上」から。軽微以上にすると震度1・2 の地震まで鳴り続けて、
通知として役に立たなくなるため（画面の絞り込みは「軽微以上」から選べる。
用途が違うので値も別に持つ）。

種別の行には対象範囲を添える（「山火事（米国のみ）」）。
選ぶその場で範囲が分からないと、通知が来ない理由に気づけない。

アプリ内で通知を ON にしていても、**端末が許可していなければ鳴らない**。
気づけないと「通知が来ない」で終わるので、設定画面の先頭で許可状態を確認し、
未許可ならその場で許可を求める（すでに拒否されていると Android は
何も出さないため、端末の設定から変える必要があることを案内する）。

## 9.5 使い方の画面

「機能はあるのに気づかれない」を避けるため、初回起動時に案内を出す。
ただし**最初に見せるのは3枚だけ**にした（`WelcomePage`）。
一度は「使い方＋データ範囲の全部」を初回に出したが、
その量を最初に読む人はいない。1枚1文にして、いつでも飛ばせるようにし、
最後は「地図をひらく」で本編に着地させている。

細かい話（種別ごとにどこまで取れているか、さかのぼれる範囲）は
`TutorialPage` に分け、設定画面と初回案内の小さなリンクから開く。
取れていない範囲を知らずに使うと「起きていない」と誤解するため、
表そのものは残してある。

出典と免責をまとめた「このアプリについて」は、普段は見ないものなので
主画面の AppBar から外し、この画面のいちばん下に畳んで置いている
（AppBar にアイコンを並べるほど、どれも見えなくなる）。

## 10. 英語の配信元の日本語化

USGS も EONET も英語でしか配信していない。
翻訳 API を使うと鍵と通信が要り、**オフラインで読めなくなる**ため、
アプリ内の辞書で定型部分だけを置き換えている（`lib/core/world_text_ja.dart`）。

- 訳す: 方角（SSE→南南東）、単位、国名、米国の州名、カテゴリ名、現象名
- 訳さない: 都市名などの固有名詞

> M 4.3 - 10 km SSE of Ocotito, Mexico
> → M4.3 メキシコ Ocotito の南南東 10km

固有名詞を無理に音訳すると現地の報道や公式発表と突き合わせられなくなるので、
原文はそのまま残し、詳細画面に「原文: …」として併記している。

和訳は**取得した時点**で行う。画面で訳すと、通知や Webhook に流れる文面だけが
英語のまま残ってしまうため。

## 10.5 通知を待たずに受け取る（リアルタイム監視）

定期取得は Android の制限で15分ごとが上限で、「揺れた直後に規模を知る」には遅い。
P2P地震情報が **WebSocket**（`wss://api.p2pquake.net/v2/ws`）を公開しているので、
つなぎっぱなしにして、発表が流れてきた瞬間に通知する
（`RealtimeMonitor`）。サーバーを持たずに秒単位にできる。

流れてくる JSON はまとめて取得したときと同じ形なので、
配列に包んで既存のパーサへ渡すだけで済む（`P2pQuakeSource.parseMessage`）。
**ID の作り方も同じになるので、定期取得と二重に鳴ることがない**
（通知済みの記録も `SeenStore` を共有している）。

代償があるので、**既定では止めてあり、設定で明示的に入れてもらう**。

- Android では常駐サービスが要る。通知バーに「監視中」が出たままになる（消せない）
- 電池を食う
- Google Play でフォアグラウンドサービスの用途申告が要る。
  `dataSync` は Android 15 で24時間あたり6時間までに制限されるため、
  継続的な災害監視として `specialUse` を宣言している
  （`PROPERTY_SPECIAL_USE_FGS_SUBTYPE = disaster_alert_monitoring`）

対象は**地震・津波だけ**。気象警報や海外の情報は定期取得のまま。
圏外や省電力で接続はよく切れるため、1分ごとに接続を確かめて張り直す。

### 緊急地震速報はこの経路では扱えない

「揺れる前に鳴る」あれは、気象庁から携帯網を通って端末の OS 機能
（エリアメール／ETWS）へ直接届くもので、アプリからは触れない。
WebSocket で速くなるのは**地震が起きた後の発表**なので、
用途は「揺れた直後に規模と震度を知る」になる。

## 10.7 パソコン版（Windows デスクトップ）

BCP の用途では「対策本部の PC で一日中開いておく」使い方が自然で、
実はスマートフォンより素直に動く。

| | Android | パソコン | Web |
|---|---|---|---|
| 端末通知 | ○ | ○（Windows のトースト） | × |
| 自動確認 | 15分ごと（端末任せ） | **5分ごと**（開いている間） | × |
| リアルタイム監視 | 常駐サービスが要る | **そのままつなぐだけ** | × |
| Webhook 送信 | ○ | ○ | ×（送信先が CORS 非対応） |

Android は端末に任せて動く仕組み（WorkManager・常駐サービス）があるが、
パソコンには無い。代わりに**アプリが開いている限り動き続ける**ので、
アプリ自身が見張る（`DesktopMonitor`）。
常駐サービスの申請も、通知バーの居座りも要らない。

通知の判定と「二重に鳴らさない」記録は、3つの経路
（Android の定期取得・常駐監視・パソコンの監視）で共通にしてある
（`EventNotifier`）。経路ごとに書くと条件がずれて「片方だけ鳴る」ため。

ビルドには Visual Studio の C++ ツールが要る。

    winget install --id Microsoft.VisualStudio.2022.BuildTools --override ^
      "--quiet --wait --norestart --add Microsoft.VisualStudio.Workload.VCTools --includeRecommended"
    flutter build windows --release

出来上がるのは単体の exe ではなく、`build/windows/x64/runner/Release/` の
フォルダ一式（exe + DLL + data）。配布するときはフォルダごと固めるか、
インストーラ（MSIX・Inno Setup など）にする。

## 12. 地図の操作をどこまで許すか

flutter_map は既定で2本指の回転を受け付ける。
実機で拡大縮小しようとすると地図が回ってしまい、北がどちらか分からなくなる。
災害時に方角を見失うのは致命的なので、回転の操作だけを外している
（`InteractiveFlag.all & ~InteractiveFlag.rotate`）。

縮小の下限は画面の実寸から計算する（`MapStyle.fitZoom`）。

**東西だけ**を見て、世界1周が画面幅にちょうど収まるところまで。
起動時の中心は日本に置き、初期ズームはそれより寄せている。

縮小の下限だけでは、横へ動かし続けると世界が延々と繰り返される。
EPSG:3857 が経度方向に世界を複製するためだ。

一度は複製そのものを切ったが、これは失敗だった。
複製を切ると地図の実体が経度 -180〜180 の1枚に固定され、
**日本を真ん中に置いた世界地図が作れなくなる**
（日本を中央にすると右側が空白になり、世界の6割が画面の外に出る）。

正しくは、**複製は有効なまま、動かせる範囲を1周分の「窓」に限る**。
`onPositionChanged` で画面の端を見て、窓から出たら中心を戻す
（`MapStyle.clampLongitude`）。窓の中心をどこに置くかで継ぎ目の位置が決まる。

### 世界地図の中心は選べる

「中心をどこに置くか」は「どこで切るか」と同じなので、設定で選べるようにした
（`WorldCenter`）。

| 中心 | 継ぎ目 | 向いている見方 |
|---|---|---|
| 日本（東経140度・既定） | 大西洋 | 太平洋を丸ごと見る |
| イギリス（経度0度） | 太平洋 | 世界地図としてよくある形 |

判定は「中心を 0 とみなした経度」に直してから行う（`shiftLongitude`）。
継ぎ目をまたぐ比較を素直に書けるようにするため。

### 種別を変えたら、その範囲を映す

選んだ時点で、その種別の情報がある範囲へ寄せる（`CameraFit.bounds`）。
日本を見たまま「山火事」を選んでも、そこには何も無いため。

- 山火事 → 米国、気象警報・津波 → 日本
- 地震・火山・台風（全世界が対象）→ 世界全体

種別と世界地図の中心のどちらが変わっても映す範囲が変わるので、
`key` を変えて地図を作り直している。

中心を動かせる範囲は、地図の端より少し外まで許している（`centerPadding`）。
ちょうどにすると、拡大したときに端の陸地を画面いっぱいに寄せられない。
flutter_map の `CameraConstraint.contain` は、条件を満たさないカメラのまま
再描画すると assert で落ちるため、中心だけを縛る `containCenter` を使う。

### 下から引き出す一覧は何のためにあるか

ピンで探せるものが並ぶだけに見えるが、
**座標を持たない情報（津波予報区など）は地図に出せない**ため、
一覧が唯一の出口になる。ピンが重なって潰れるときにも要る。
見出しに「一覧（新しい順）・◯件」と「地図に出せない情報 ◯件」を出して、
役割が分かるようにした。初期の高さは地図を広く見せる側に寄せている。

「通知対象 ◯件」の帯はアプリ版では出さないことにした。
Web 版には端末通知が無いので見本として要るが、
アプリ版では実際に通知が飛ぶうえ、数字だけでは何を指すのか伝わらなかった。

### 下から引き出す一覧のつまみ

`DraggableScrollableSheet` は、中のスクロール領域を指でなぞったときだけ動く。
つまみ（横棒）はその外側にあるため、つまみを引いても何も起きず、
「反応する位置がずれている」ように感じる。
つまみ自身に `onVerticalDragUpdate` を付けて
`DraggableScrollableController` を直接動かし、当たり判定も横棒の周りごと
28px 分取っている（タップでも開閉する）。

詳細を出したときは、一覧と同じ地の色だと境目が見えないため、
一段濃い面（`surfaceContainerHighest`）と上辺の線で分けている。
